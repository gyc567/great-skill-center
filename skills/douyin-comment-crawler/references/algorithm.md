# a_bogus 签名算法原理

本文说明抖音 web 接口 `a_bogus` 参数的生成原理。实现见 `../scripts/abogus.py`。

## 为什么要签名

抖音 web 端接口（`/aweme/v1/web/comment/list/` 等）要求每个请求携带 `a_bogus` 参数。
它是把「请求参数 + 时间戳 + User-Agent + 浏览器环境」做一次混合运算后的结果，
服务端用同样算法重算并比对，不一致就拒绝。

表现形态很关键：**签名不对时，HTTP 层依然返回 200，但响应体是空的**。
所以「接口返回 200」绝不代表成功。

## 算法分解

整体流程：

```text
查询串 ──► SM3(SM3(query + "cus"))  ──► params_hash
"cus"   ──► SM3(SM3("cus"))           ──► suffix_hash
UA      ──► RC4(UA, key) ──► b64 ──► SM3 ──► ua_hash
                     │
时间戳、参数、浏览器环境 ──► 字节数组 b ──► 排序 ──► RC4 ──► 随机前缀拼接 ──► 自定义 base64
```

### 1. SM3 杂凑

国密算法，标准 `GB/T 32905-2016`。

**最容易写错的地方**（本项目踩过）：

```python
tt1 = (FF(a,b,c,j) + d + ss2 + w1[j]) & 0xFFFFFFFF   # ← 用 W1[j]
tt2 = (GG(e,f,g,j) + h + ss1 + w[j])   & 0xFFFFFFFF   # ← 用 W[j]
```

`TT1` 用 `W1[j]`（异或扩展字），`TT2` 用 `W[j]`（原字）。写反不会抛异常，
只是摘要完全错误 → 签名被拒 → 空响应。

标准验证向量：

| 输入 | 期望摘要 |
|---|---|
| `"abc"` | `66c7f0f462eeedd9d1f2d46bdc10e4e24167c4875cf2f7a2297da02b8f4ba8e0` |
| `"abcd"` ×16 | `debe9ff92275b8a138604889c18e5a4d6fdb70e5387e5765293dcba39c0c5732` |
| `""` | `1ab21d8355cfa17f8e61194831e81a8f22bec8c728fefb747ed035eb5082aa2b` |
| `"a"` ×1000 | `f4bedca973227d45c5b822551d2e762d4cfb0e9af70b241452545727b5fb046f` |

### 2. RC4

经典 KSA/PRGA 流密码。

两处用途：

- **UA 加密**：key = `bytes([0, 1, arg2])`，即 JS 里 `String.fromCharCode(0.00390625, 1, arg2)`
  （`0.00390625` 在 `fromCharCode` 中被截断为 `0`）。
- **主签名**：key = `b"y"`。

### 3. 自定义 Base64

抖音用了标准 base64 的字母表替换变体，共 `s0`~`s4` 五张表，签名用 `s4`。

**长度规则容易错**：原实现是

```javascript
for (let i = 0; i < long_str.length / 3 * 4; i++) { ... }
```

循环上界是**浮点数**。所以：

| 输入字节数 | `len/3*4` | 实际输出字符数 |
|---|---|---|
| 108 | 144.0 | 144 |
| 109 | 145.33 | 145 |
| 110 | 146.67 | **147** |
| 111 | 148.0 | 148 |

即 `ceil(len * 4 / 3)`，比标准 base64 少一个 padding 位。

### 4. 字节数组 b 与排序

签名载荷是一个下标从 0 开始的不连续字节数组 `b`：

| 下标 | 含义 |
|---|---|
| `b[8]` | 固定值 3 |
| `b[10]` | 结束时间戳（毫秒） |
| `b[16]` | 开始时间戳（毫秒） |
| `b[18]`, `b[19]` | 固定 44 |
| `b[20]`~`b[25]` | 开始时间戳的字节拆分 |
| `b[26]`~`b[37]` | 三个签名参数 arg0/arg1/arg2 的字节拆分 |
| `b[38]`,`b[39]` | `params_hash[21]`, `params_hash[22]` |
| `b[40]`,`b[41]` | `suffix_hash[21]`, `suffix_hash[22]` |
| `b[42]`,`b[43]` | `ua_hash[23]`, `ua_hash[24]` |
| `b[44]`~`b[50]` | 结束时间戳的字节拆分 |
| `b[51]`~`b[60]` | 固定 `page_id=6241` / `aid=6383` |
| `b[64]`~`b[66]` | 浏览器环境串长度及其字节 |
| `b[69]`~`b[71]` | 固定 0 |
| `b[72]` | 前面所有字节的异或校验 |

**时间戳拆分用的是浮点除法**，不是移位：

```python
b[24] = int(b[16] / 256 / 256 / 256 / 256) & 0xFF
b[25] = int(b[16] / 256 / 256 / 256 / 256 / 256) & 0xFF
```

写成 `b[16] >> 16` 会得到不同的值，导致签名不一致。

**异或校验 `b[72]`** 要按固定顺序异或 44 个字节：

```text
b[18] b[20] b[26] b[30] b[38] b[40] b[42] b[21] b[27] b[31] b[35] b[39] b[41]
b[43] b[22] b[28] b[32] b[36] b[23] b[29] b[33] b[37] b[44] b[45] b[46]
b[47] b[48] b[49] b[50] b[24] b[25] b[52] b[53] b[54] b[55] b[57] b[58]
b[59] b[60] b[65] b[66] b[70] b[71]
```

### 5. 组装与输出

```text
bb = bytes(order) + window_env + bytes([b[72]])
```

- `order` 是 44 个字节的固定取用顺序（见 `abogus.py` 的 `order` 列表）
- `window_env` 是 65 字节的浏览器环境串
- 整体共 110 字节

最后：

```python
random_prefix = generate_random_str()      # 12 字节，3 × 4
signature = custom_b64(random_prefix + rc4(bb, b"y"), "s4") + "="
```

签名长度 = `ceil(122 * 4 / 3) + 1` = **164** 字符。

`random_prefix` 由三次 `gener_random` 组成，每次产出 4 字节，字节值被约束在
指定区间内（用于模拟真实的随机分布）。

## 签名参数组合

不同接口用不同的 `(arg0, arg1, arg2)`：

| 接口 | 参数组 |
|---|---|
| 评论列表 `/comment/list/` | `(0, 1, 8)` |
| 评论回复 `/comment/list/reply/` | `(0, 1, 8)` |
| 视频详情 `/aweme/detail/` | `(0, 1, 14)` |

`arg2` 会参与 UA 加密 key 的构造（`bytes([0, 1, arg2])`），所以换参数组必须重新计算 UA 摘要。

## 请求侧要求

签名用的查询串和实际发出的请求必须**逐字节一致**：

- 参数顺序相同
- URL 编码方式相同（本项目用 `urllib.parse.quote(v, safe="")`）
- `a_bogus` 自身不参与签名

实现上用同一个 dict 先算签名、再发请求，从结构上避免两边跑偏：

```python
query = _build_query(params)               # 签名前的串
signed = dict(params)
signed["a_bogus"] = sign(query, ua, args)  # 加签名
await client.get(url, params=signed)       # 发出
```

## 不要引入随机 msToken

`msToken` 是浏览器端生成的会话标识，**只能来自真实 Cookie**。
用随机字符串冒充并参与签名，会让服务端判定签名无效，返回空响应。

症状：HTTP 200 + 空 body + 无错误码。
本项目 `WEB_PARAMS` 刻意不含 `msToken`，并有回归测试守护。

## 交叉验证

上游实现是 JavaScript（需 Node.js + execjs）。本项目是纯 Python。

对同一查询串，两者输出的签名：

- 长度完全一致（164 字符）
- 中后段大范围逐字符相同
- 差异仅在随机前缀和毫秒级时间戳（每次调用本来就不同）

更强的验证是**真实请求**：纯 Python 实现已被抖音服务端接受，
实测取到一级评论 25 条、二级回复 2 条的真实数据。
